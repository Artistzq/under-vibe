## 前言

> 💡 **场景重现**
>
> AI 对你说："把 API 密钥写进环境变量，然后重启一下终端"
>
> 你："环境变量是什么？为什么要重启？写到哪里去了？"

上篇「环境」里，`command not found`、PATH、"装完要重启才生效"反复出现，背后其实指向同一个概念：**环境变量**。它是操作系统和程序之间传递"全局设置"的标准方式，也是你以后被 AI 要求"配个密钥""改个端口""把某个目录加进 PATH"时的操作对象。

本篇讲清楚三件事：环境变量**是什么**、怎么**查看**、怎么**修改**，以及为什么"改完要等一等"才生效。

::: tip 💡 一句话记住环境变量
**环境变量**（Environment Variable）就是一条"名字 = 值"的全局设置。程序启动时会读取它，从而改变程序的行为——它不是写在程序代码里的，而是启动前由外部准备好的一批值。
:::

## 什么是环境变量

### 1. 名字 = 值的键值对

每个环境变量都形如 `名字=值`，例如 `PATH=/usr/local/bin:/usr/bin:/bin`。名字通常是全大写（`PATH`、`HOME`），值是一段文本。整台系统上挂着几十上百个这样的"名字 = 值"条目，它们共同构成所谓的**环境**（Environment，这里的"环境"特指这套键值对的集合）。

::: tip 💡 通俗类比
环境变量像餐厅柜台里的一张"固定菜单"：上面写着"默认口味""餐具偏好"等条目（名字）和对应的选择（值）。每桌新客人（新启动的程序）一坐下，服务员就先抄一份这份菜单，照它上菜。
:::

### 2. 谁在用它

环境变量是程序读取外部设置最常见的方式之一：

- **Shell** 靠 `PATH` 决定去哪里找命令（上篇讲过）
- **程序** 靠它决定行为：语言编码、服务器端口、API 地址等
- **操作系统** 用 `HOME`、`USER` 记录"当前用户是谁、主文件夹在哪"

下表是几个最常见的环境变量：

| 变量 | 作用 |
|------|------|
| `PATH` | 命令解释器按此目录列表查找命令 |
| `HOME` | 当前用户的主文件夹（Windows 常用 `USERPROFILE`） |
| `USER` / `USERNAME` | 当前用户名 |
| `SHELL` | 默认命令解释器的路径 |
| `LANG` | 系统默认语言与字符编码 |

::: tip 💡 不用背
这张表不是考纲。先记住"环境变量 = 名字 = 值的全局设置"，遇到具体的（比如 `LANG` 乱码、`HOME` 不对）再回来查。
:::

## 实战：查看环境变量

### 1. 查看某一个变量

```bash
# macOS / Linux
echo $PATH
echo $HOME

# Windows PowerShell
$env:PATH
$env:USERPROFILE
```

::: tip 💡 `$` 与 `$env:` 是什么
macOS / Linux 里，`$变量名` 表示"取出这个变量的值"，`echo $PATH` 就是"打印 PATH 的值"。Windows PowerShell 的写法是 `$env:变量名`，`env` 表示环境变量。两种写法里的 `$` 都是"取值"记号，不是变量名的一部分。
:::

### 2. 查看全部环境变量

```bash
# macOS / Linux
env

# Windows PowerShell
Get-ChildItem Env:
```

输出是一长串 `名字=值`，从头到尾读一遍，就能看到整台系统给程序准备的"全局设置"长什么样。

::: tip 💡 试试看
运行 `env` 之后，用 `env | grep PATH`（macOS / Linux）或 `Get-ChildItem Env: | Select-String PATH`（Windows）筛选一下——上篇见过的 `PATH` 就藏在里面。
:::

## 实战：修改环境变量

修改环境变量分两种情况：**临时**（只对当前终端窗口生效）与**永久**（写进配置文件，每次开终端都生效）。

### 1. 临时修改：只对当前窗口

```bash
# macOS / Linux
export MY_VAR=hello
echo $MY_VAR     # 输出 hello

# Windows PowerShell
$env:MY_VAR = "hello"
$env:MY_VAR      # 输出 hello
```

::: warning ⚠️ 临时修改的边界
临时修改只存在于**当前终端窗口**：关掉窗口、或另开一个新终端，值就没了。程序读取环境变量是在**启动那一刻**，所以对正在运行的程序改变量，它也不会感知到。
:::

### 2. 永久修改：写进配置文件

macOS / Linux 的 Shell 在每次启动时会自动执行一个配置文件（macOS 默认 zsh 读 `~/.zshrc`；Linux 的 bash 读 `~/.bashrc`）。把 `export` 写进去，就能每次开终端自动生效：

```bash
# macOS / Linux（以 zsh 为例）
echo 'export MY_VAR=hello' >> ~/.zshrc
source ~/.zshrc       # 立即重读一次配置，不必重开终端

# Windows PowerShell（两种方式二选一）
setx MY_VAR "hello"                # 命令方式：对新开的窗口生效
# 或：设置 → 系统 → 关于 → 高级系统设置 → 环境变量（图形界面）
```

::: warning ⚠️ Windows 的 setx 有"延迟"
`setx` 修改后，**当前已打开的窗口不会生效**，要新开一个终端窗口才行。这是 Windows 与 macOS / Linux 在"生效时机"上的一个典型差异。
:::

### 3. 修改 PATH：往"找命令的目录列表"里加一项

PATH 的值是一串目录，用冒号（macOS / Linux）或分号（Windows）分隔。往里加新目录时，**必须先取出原有内容，再追加**，否则会把整个 PATH 覆盖掉：

```bash
# macOS / Linux（临时，示范追加 /my/tools/bin）
export PATH="$PATH:/my/tools/bin"

# Windows PowerShell（临时，示范追加 C:\my\tools\bin）
$env:PATH = "$env:PATH;C:\my\tools\bin"
```

::: warning ⚠️ 别丢掉原来的 PATH
`$PATH`（或 `$env:PATH`）先取出原值，再拼上新目录。如果写成 `export PATH=/my/tools/bin`，PATH 就只剩这一项，连 `ls`、`cd` 都会提示找不到——因为系统找不到这些命令的位置了。
:::

::: tip 💡 什么时候需要改 PATH
安装了一些"命令行工具"（如某些语言工具链、单文件脚本），它们装好后不在默认目录里，需要把所在目录加进 PATH，命令才能被直接调用。装完提示"重启终端或重新登录"的，多半就是这类修改。
:::

### 4. 项目级：`.env` 文件（预告）

很多项目把环境变量集中写进项目根目录的一个 `.env` 文件，由工具（如 Node 生态的 dotenv）读取后注入程序。它是"这个项目自己的一套环境变量"，与全局的 Shell 配置分开：

```text
# 项目根目录的 .env 文件
API_KEY=sk-xxxx
PORT=3000
```

::: warning ⚠️ 密钥别进代码仓库
`.env` 里常放着 API 密钥等敏感信息，**不应提交到版本管理**（Git，后续章节会讲），应加进 `.gitignore` 忽略清单。`.env` 的详细机制在第二站「配置文件」展开，这里先认识它即可。
:::

## 原理简析：为什么"改完要重启才生效"

### 1. 环境变量随进程"复制"传递

程序不是从配置文件里现场查环境变量，而是在**启动那一刻**，把父进程的环境变量整套"复印"一份，带进自己进程里：

```mermaid
graph LR
    classDef u fill:#e6f7ff,stroke:#1890ff
    classDef t fill:#f0f2f5,stroke:#333
    classDef s fill:#fff7e6,stroke:#fa8c16
    classDef k fill:#fef0f0,stroke:#f5222d
    classDef r fill:#f0fff4,stroke:#52c41a

    A[系统启动<br/>建立环境变量]:::u -->|打开终端| B[Shell<br/>复制一份到内存]:::t
    B -->|运行命令 node / python<br/>每次启动都继承| C[程序进程<br/>启动瞬间读取整套]:::s
    C -->|程序需要时| D[取某个名字的值<br/>getenv / process.env]:::k
    D -->|得到值| E[程序行为随之改变]:::r
```

这就是"临时修改只对当前窗口生效"的原因：**每个进程用的是自己启动那一刻的那份拷贝**。终端 A 里 `export` 的值，只进了 A 及它启动的子进程；终端 B 是另一份拷贝，看不到 A 的改动。

::: tip 🛵 打个比方
环境变量像入职时复印的"员工手册"：每人（每个进程）手里都是入职当天那一版。后来公司更新了手册，老员工手里的旧版不会自动换新——要重新领一份（重启程序）才会拿到新版。
:::

### 2. 配置文件只是"下次启动要执行的脚本"

macOS / Linux 的 `~/.zshrc`、`~/.bashrc` 本质是**脚本**：只有 Shell 启动时才会执行一遍。修改文件本身，不会影响任何已经运行的 Shell。所以有两种方式让改动生效：

- 重开终端（让 Shell 重新启动、重新执行配置文件）
- 执行 `source ~/.zshrc`（手动在当前 Shell 里再执行一遍配置文件）

Windows 的 `setx` 与图形界面修改同理：改动写入系统设置，**新启动的程序**才会读到新值。

::: tip ⚠️ 简化说明
真实的机制还包括 `setenv`、环境变量表在内存中的布局等细节。但"启动时快照 + 子进程继承"这两点，已经足够解释"为什么改完要重开终端""为什么两个窗口互不影响"这些日常现象。
:::

### 3. 程序怎么读到自己想要的值

程序运行时通过操作系统提供的接口查询：C 语言用 `getenv`，Node.js 用 `process.env`，Python 用 `os.environ`。它们本质上都是"在这份启动时拷贝里，按名字找一个值"。查不到就返回空，程序再决定用默认值还是报错。

## 避坑指南

### 坑 1：改完没生效

改完终端里 `echo $MY_VAR` 还是空？先分清改的是哪种：

- **临时修改**：只对当前窗口有效，新开窗口当然没有
- **永久修改**：写进配置文件后要 `source` 一次或重开终端；Windows 用 `setx` 后要新开窗口

::: tip 💡 通用原则
程序读环境变量是在**启动那一刻**。改动后，让"要用它的那个程序"重新启动即可，不必卸载重装。
:::

### 坑 2：把 PATH 整个覆盖了

`export PATH=/new/dir` 这种写法会丢掉原来的 PATH，导致 `ls`、`cd`、`node` 等常用命令全部提示找不到。若真发生了：

- 临时修改：直接关掉这个终端窗口重开，原 PATH 就回来了（只要没写进配置文件）
- 永久修改：若已写进配置文件，删掉那行再 `source` 恢复

**正确写法永远是 `export PATH="$PATH:新目录"`**，把原值带上。

### 坑 3：值里有空格或特殊字符

值含空格时要加引号，否则 Shell 会把值拆成多段：

```bash
# macOS / Linux
export MY_VAR="hello world"

# Windows PowerShell
$env:MY_VAR = "hello world"
```

Windows 的 `setx` 遇到含 `%` 的值还会发生变量展开（如把 `%PATH%` 展开成实际路径），需要谨慎。

### 坑 4：Windows 上搞混"生效时机"

`setx` 与图形界面修改都只影响**新启动的**程序；已打开的窗口和正在运行的程序读到的是旧值。改完系统环境变量却"没生效"，先重开终端、重启程序，不要急着怀疑改错了。

### 坑 5：把密钥写进 Shell 配置文件

把密码、API 密钥写进 `~/.zshrc`、`~/.bashrc` 或项目代码里，容易随文件泄露（比如被提交到仓库）。**敏感信息应放 `.env` 文件（不进版本管理）**，或用专门的密钥管理工具，而不是写进会被共享、备份、提交的文本文件。

### 坑 6：混淆环境变量名的大小写

macOS / Linux 的环境变量名**区分大小写**：`$HOME` 有值、`$home` 是空。Windows 环境变量名不区分大小写，但约定俗成仍用大写。照抄命令时注意大小写。

::: tip 💡 忘了变量名怎么办
不确定环境变量叫什么，先 `env`（macOS / Linux）或 `Get-ChildItem Env:`（Windows）把全部列出来找，别凭记忆猜。
:::

## 拓展阅读

### 环境变量、环境与配置文件：三个粒度

「环境」一篇讲的"环境"是语言、运行时、包管理器那套软件；环境变量是其中**进程级**的"全局设置"（键值对）；而第二站要讲的配置文件（`.json`、`.yaml`、`.env`）是**项目级**的设置。三者粒度不同：一套软件管"能不能跑"，一套键值对管"跑成什么样"，一份项目配置管"这个项目具体怎么跑"。

### 下一篇预告

环境变量解决的是"程序启动时读哪些全局设置"。可项目要真正跑起来，还得从仓库取回一批它依赖的第三方代码——版本不符、装错位置、清单缺失，都是它报错的常见姿势。下一篇将讲解「依赖」：项目为什么跑不起来。

## 📖 术语表

| 术语 | 一句话解释 |
|------|-----------|
| **环境变量 (Environment Variable)** | 一条"名字 = 值"的全局设置，程序启动时读取 |
| **键值对 (Key-Value Pair)** | 一个名字对应一个值的数据形式，如 `PATH=/usr/bin` |
| **PATH** | 环境变量，命令解释器按它列出的目录顺序查找命令 |
| **HOME** | 环境变量，当前用户主文件夹的路径 |
| **export** | macOS / Linux 中设置（导出）环境变量的命令 |
| **setx** | Windows 中永久设置环境变量的命令 |
| **source** | 在当前 Shell 中重新执行配置文件，让修改立即生效 |
| **配置文件** | Shell 启动时自动执行的脚本，如 `~/.zshrc`、`~/.bashrc` |
| **进程 (Process)** | 正在运行的一个程序实例；每个进程持有启动那一刻的环境变量拷贝 |
| **getenv / process.env / os.environ** | 程序读取环境变量的接口（C / Node.js / Python） |
| **.env** | 项目级环境变量清单文件，通常不进版本管理 |
