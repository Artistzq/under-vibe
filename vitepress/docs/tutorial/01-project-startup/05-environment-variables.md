## 前言

> 💡 **场景重现**
>
> AI 对你说："把 API 密钥写进环境变量，然后重启一下终端"
>
> 你："环境变量是什么？为什么要重启？"

上篇「环境」里反复出现的 PATH、`command not found`、"装完要重启才生效"，其实都指向同一个概念：**环境变量**——程序的全局设置。本篇讲清楚它是什么、怎么查看和修改，以及为什么"改完要等一等"才生效。

::: tip 💡 一句话记住
**环境变量**（Environment Variable）就是一条"名字 = 值"的全局设置。程序启动时会读取它，从而改变程序的行为——它不是写在代码里的，而是启动前由外部准备好的一批值。
:::

## 什么是环境变量

每个环境变量都形如 `名字=值`，例如 `PATH=/usr/local/bin:/usr/bin:/bin`。名字通常全大写（`PATH`、`HOME`），值是一段文本。几十上百个这样的条目合在一起，就是程序启动时看到的"环境"。

::: tip 💡 通俗类比
环境变量像餐厅柜台里的一张"固定菜单"：写着"默认口味""餐具偏好"等条目（名字）和对应的选择（值）。每桌新客人（新启动的程序）一坐下，服务员就先抄一份菜单，照它上菜。
:::

谁在用环境变量？

- **Shell** 靠 `PATH` 决定去哪里找命令（上篇讲过）
- **程序** 靠它决定行为：语言编码、服务器端口、API 地址等
- **操作系统** 用 `HOME`、`USER` 记录"当前用户是谁、主文件夹在哪"

常见的几个：

| 变量 | 作用 |
|------|------|
| `PATH` | 命令解释器按此目录列表查找命令 |
| `HOME` | 当前用户的主文件夹（Windows 常用 `USERPROFILE`） |
| `USER` / `USERNAME` | 当前用户名 |

::: tip 💡 不用背
记住"环境变量 = 名字 = 值的全局设置"就够。遇到具体的（比如 `LANG` 乱码、`HOME` 不对）再回来查。
:::

## 实战：查看环境变量

```bash
# macOS / Linux
echo $PATH        # 查看某一个
env               # 查看全部

# Windows PowerShell
$env:PATH         # 查看某一个
Get-ChildItem Env:  # 查看全部
```

::: tip 💡 `$` 与 `$env:` 是什么
macOS / Linux 里，`$变量名` 表示"取出这个变量的值"；Windows PowerShell 的写法是 `$env:变量名`。两种写法里的 `$` 都是"取值"记号。
:::

`env` 的输出是一长串 `名字=值`，读一遍就能看到整台系统给程序准备的"全局设置"长什么样。

## 实战：修改环境变量

修改分两种：**临时**（只对当前终端窗口生效）与**永久**（写进配置文件，每次开终端都生效）。

### 1. 临时修改

```bash
# macOS / Linux
export MY_VAR=hello
echo $MY_VAR      # 输出 hello

# Windows PowerShell
$env:MY_VAR = "hello"
$env:MY_VAR       # 输出 hello
```

::: warning ⚠️ 临时修改的边界
临时修改只存在于**当前终端窗口**：关掉窗口、或另开一个新终端，值就没了。程序读取环境变量是在**启动那一刻**，所以对正在运行的程序改变量，它也不会感知到。
:::

### 2. 永久修改：写进配置文件

macOS / Linux 的 Shell 每次启动时会自动执行一个配置文件（macOS 默认 zsh 读 `~/.zshrc`；Linux 的 bash 读 `~/.bashrc`）。把 `export` 写进去，每次开终端自动生效：

```bash
# macOS / Linux（以 zsh 为例）
echo 'export MY_VAR=hello' >> ~/.zshrc
source ~/.zshrc       # 立即重读一次配置，不必重开终端

# Windows PowerShell（二选一）
setx MY_VAR "hello"                # 命令方式：对新开的窗口生效
# 或：设置 → 系统 → 关于 → 高级系统设置 → 环境变量（图形界面）
```

::: warning ⚠️ Windows 的 setx 有"延迟"
`setx` 修改后，**当前已打开的窗口不会生效**，要新开一个终端窗口。这是 Windows 与 macOS / Linux 在"生效时机"上的典型差异。
:::

### 3. 修改 PATH：往"找命令的目录列表"里加一项

PATH 的值是一串目录，用冒号（macOS / Linux）或分号（Windows）分隔。加新目录时**先取出原值再追加**，否则会把整个 PATH 覆盖掉：

```bash
# macOS / Linux（临时，追加 /my/tools/bin）
export PATH="$PATH:/my/tools/bin"

# Windows PowerShell（临时，追加 C:\my\tools\bin）
$env:PATH = "$env:PATH;C:\my\tools\bin"
```

::: warning ⚠️ 别丢掉原来的 PATH
写成 `export PATH=/my/tools/bin` 会把 PATH 整个覆盖，连 `ls`、`cd` 都会提示找不到。**正确写法永远把 `$PATH` 带上。**
:::

::: tip 💡 什么时候需要改 PATH
装了一些命令行工具（如语言工具链），它们不在默认目录里，把所在目录加进 PATH 后命令才能被直接调用。装完提示"重启终端或重新登录"的，多半就是这类修改。
:::

## 原理简析：为什么"改完要重启才生效"

程序不是在每次读取时去文件里查环境变量，而是在**启动那一刻**，把父进程的环境变量整套"复印"一份，带进自己进程里：

```mermaid
graph LR
    classDef u fill:#e6f7ff,stroke:#1890ff
    classDef t fill:#f0f2f5,stroke:#333

    classDef k fill:#fef0f0,stroke:#f5222d
    classDef r fill:#f0fff4,stroke:#52c41a

    A[系统启动<br/>建立环境变量]:::u -->|打开终端| B[Shell<br/>复制一份到内存]:::t
    B -->|运行命令 node / python<br/>每次启动都继承| C[程序进程<br/>启动瞬间读取整套]:::s
    C -->|程序需要时| D[取某个名字的值<br/>getenv / process.env]:::k
    D -->|得到值| E[程序行为随之改变]:::r
```

所以：**每个进程用的是自己启动那一刻的那份拷贝**。终端 A 里 `export` 的值，只进了 A 及它启动的子进程；终端 B 看不到 A 的改动。程序需要取值时，通过操作系统接口查这份拷贝：C 语言用 `getenv`，Node.js 用 `process.env`，Python 用 `os.environ`。

::: tip 🛵 打个比方
环境变量像入职时复印的"员工手册"：每人（每个进程）手里都是入职当天那一版。后来公司更新了手册，老员工手里的旧版不会自动换新——要重新领一份（重启程序）才会拿到新版。
:::

配置文件（`~/.zshrc`、`~/.bashrc`）本质是**脚本**：只有 Shell 启动时才执行一遍，修改文件本身不影响已经运行的 Shell。所以让改动生效有两种方式：

- 重开终端（Shell 重新启动、重新执行配置文件）
- 执行 `source ~/.zshrc`（手动在当前 Shell 里再执行一遍配置文件）

::: tip ⚠️ 简化说明
真实机制还包括 `setenv`、内存中的环境变量表等细节。但"启动时快照 + 子进程继承"这两点，已足够解释日常现象。
:::

## 避坑指南

### 坑 1：改完没生效

先分清改的是哪种：

- **临时修改**：只对当前窗口有效，新开窗口当然没有
- **永久修改**：写进配置文件后要 `source` 一次或重开终端；Windows 用 `setx` 后要新开窗口

::: tip 💡 通用原则
程序读环境变量是在**启动那一刻**。改动后，让"要用它的那个程序"重新启动即可，不必卸载重装。
:::

### 坑 2：把 PATH 整个覆盖了

`export PATH=/new/dir` 会丢掉原来的 PATH，常用命令全部提示找不到。临时修改的话，直接关掉窗口重开就恢复了；已写进配置文件则删掉那行再 `source`。**正确写法永远是 `export PATH="$PATH:新目录"`。**

### 坑 3：把密钥写进 Shell 配置文件

把密码、API 密钥写进 `~/.zshrc`、`~/.bashrc` 或项目代码，容易随文件泄露（比如被提交到仓库）。敏感信息应放 `.env` 文件（不进版本管理），或使用专门的密钥管理工具。

## 拓展阅读

### 项目级：`.env` 文件

很多项目把环境变量写进项目根目录的 `.env` 文件，由工具读取后注入程序，是"这个项目自己的一套环境变量"。详细机制在第二站「配置文件」展开。

### 环境变量、环境与配置文件：三个粒度

「环境」一篇讲的是语言、运行时、包管理器那套软件；环境变量是其中**进程级**的"全局设置"；第二站要讲的配置文件（`.json`、`.yaml`、`.env`）是**项目级**的设置。三者粒度不同：一套软件管"能不能跑"，一套键值对管"跑成什么样"，一份项目配置管"这个项目具体怎么跑"。

### 下一篇预告

环境变量解决的是"程序启动时读哪些全局设置"。可项目要真正跑起来，还得从仓库取回一批它依赖的第三方代码——版本不符、装错位置、清单缺失，都是它报错的常见姿势。下一篇将讲解「依赖」：项目为什么跑不起来。

## 📖 术语表

| 术语 | 一句话解释 |
|------|-----------|
| **环境变量 (Environment Variable)** | 一条"名字 = 值"的全局设置，程序启动时读取 |
| **键值对 (Key-Value Pair)** | 一个名字对应一个值的数据形式，如 `PATH=/usr/bin` |
| **PATH** | 环境变量，命令解释器按它列出的目录顺序查找命令 |
| **HOME** | 环境变量，当前用户主文件夹的路径 |
| **export** | macOS / Linux 中设置（导出）环境变量的命令 |
| **setx** | Windows 中永久设置环境变量的命令 |
| **source** | 在当前 Shell 中重新执行配置文件，让修改立即生效 |
| **配置文件** | Shell 启动时自动执行的脚本，如 `~/.zshrc`、`~/.bashrc` |
| **进程 (Process)** | 正在运行的一个程序实例；每个进程持有启动那一刻的环境变量拷贝 |
| **.env** | 项目级环境变量清单文件，通常不进版本管理 |
