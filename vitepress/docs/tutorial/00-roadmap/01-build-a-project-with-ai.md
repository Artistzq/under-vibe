## 前言

假设你一点代码都不会写，但想让 AI 帮你做出一个真正的项目——一个能点开、能用、能给别人看的东西。你大概想象过这个画面：对着 AI 说几句话，它就噼里啪啦帮你把项目做出来了。

这个想象基本是对的，AI 确实能完成大量代码工作。但如果你只把"让 AI 干活"当作全部，很快就会卡在一个尴尬的地方：

> AI 说"请执行 `npm install`"，你不知道那是什么；
> AI 说"端口被占用"，你不知道什么是端口；
> AI 改了三轮，网页还是白屏，你既不知道问题在哪，也不知道该不该信它。

这一章就是为这个时刻准备的。它不教任何具体操作，而是先把**整段旅程**摊开给你看：和 AI 一起做一个项目，从想法到上线，到底会经历哪些阶段，每个阶段你会看到什么现象，以及这些现象背后藏着哪些你迟早要补的知识。

::: tip 💡 这一章是什么 / 不是什么
**是**：整段旅程的路线地图，告诉你"接下来会去哪、为什么去"。
**不是**：操作教程。这一章不做任何具体操作，具体怎么做，从下一章开始逐个阶段展开。
:::

::: tip 💡 一句话记住这门课
不是把读者训练成**脱离 AI 的程序员**，而是训练成能够**驾驭 AI、理解项目、并对最终结果负责**的项目建设者。
:::

## 主线：一段会贯穿整个课程的旅程

这门课围绕一条**主线**展开：你和一个 AI 助手一起，把一个真实项目从零做到上线。下面是这条线会经历的阶段，顺序即学习顺序：

```text
提出需求
  → 创建项目
  → 配置环境
  → 安装依赖
  → 启动项目
  → 修改功能
  → 浏览器与服务器通信
  → 保存数据
  → 处理错误
  → 使用 Git 保存版本
  → 部署和分享
```

::: tip 💡 为什么用"主线 + 项目"的方式学？
传统计算机课按学科组织：先学操作系统，再学网络，再学编译原理……每门都自成体系，但对一个只想"做出项目"的人来说，学完第一门可能就已经放弃了。主线方式反过来：**知识在真正需要它的时候才出现**。你不先学"什么是操作系统"，而是在"项目为什么跑不起来"的时候，才知道自己需要了解进程和端口。
:::

## 路线地图：每个阶段你会看到什么

下表是整段旅程的全景。每一行对应主线上的一个阶段：左列是阶段，中间是**读者（你）实际看到的现象**，右列是这个阶段背后**后续要学的知识**（对应到课程里就是这一阶段的理论文章）。

| 阶段 | 读者看到的现象 | 后续要学习的知识 |
|---|---|---|
| 创建项目 | AI 创建出很多文件 | 文件系统、项目结构 |
| 安装依赖 | AI 执行安装命令，下载大量东西 | 包管理器、网络、依赖 |
| 启动项目 | AI 执行开发命令，出现提示文字 | 进程、端口、运行时 |
| 浏览器访问 | 浏览器里出现本地网页 | HTTP、客户端、服务端 |
| 保存数据 | 项目里多出 JSON 文件或数据库 | 存储、数据结构 |
| 出现错误 | AI 修改代码，反复尝试 | 错误信息、状态、调试 |
| 项目上线 | AI 配置部署，生成一个网址 | 构建、服务器、权限、Git |
| AI 卡住 | AI 来回打转，不知道下一步 | 搜索、验证、人工接管 |

::: tip 💡 怎么看这张表
你不需要现在记住任何一行。它是一张**地图**：学完整门课，你会走完这些行；学完每一章，你会明白其中一行背后的知识。迷路的时候，回来看看自己走到哪了。
:::

## 双线结构：主线 + 理论线

主线是"做项目"这条实践线。但项目推进过程中，你会不断遇到新名词、新现象，它们不可能塞进主线里讲完——所以课程还有一条**理论线**：主线里冒出来的问题，就地引出对应的知识。

```text
AI 执行 npm install        →  命令、终端、网络、依赖、文件系统
AI 启动 npm run dev        →  进程、运行时、端口、环境变量
浏览器访问 localhost       →  HTTP、客户端、服务端、DNS、API
项目需要保存数据           →  JSON、文件、数据库、缓存、数据结构
AI 遇到报错               →  错误信息、执行流程、状态、日志、调试
项目需要上线               →  构建、部署、服务器、权限、Git、回滚
```

理论线必须回答一个问题：**它解释了主线中的哪个现象？** 如果某块知识暂时对应不上主线，就放进支线知识库，而不是打断主线。

::: tip 💡 类比
主线像开车去一个陌生城市：你跟着导航一路走。理论线像是经过每个路口时，导航顺口告诉你"这个路口为什么叫这个名字"。你不会在每个路口停下来上完一整节交通课——只有真正需要时才深入。
:::

## 三件套：阶段总结、Build Lab 实验、支线知识库

为了让"看懂"变成"真的会"，每个阶段学习完之后，会给你三样东西：

**1. 阶段总结**——把这个阶段主线 + 理论线的内容串起来，确认你站在了地图的哪个位置。

**2. Build Lab 手动实验**——集中到一个专题，**关掉 AI，自己动手**，把刚学的知识亲手做一遍。

::: tip 💡 手动实验不是"退回到手写代码"
实验的目的不是让你以后不用 AI，而是让你形成一张**完整的系统地图**：你知道命令是怎么敲的、文件是怎么组织的、进程是怎么启动和停掉的。有了这张地图，AI 做每一步的时候你才看得懂，AI 出错的时候你才知道往哪里查。
:::

例如第一阶段（项目启动）之后，会安排"手动启动一个项目"实验，你将完全不依赖 AI，亲手完成：创建项目目录 → 进入目录 → 创建和查看文件 → 检查运行时版本 → 安装依赖 → 启动项目 → 停止进程 → 观察项目结构，并解释每一步产生了什么变化。后续还有手动检查已有项目、手动观察一次网络请求、手动制造并排查错误、手动修改保存和回退版本等实验。

**3. 支线知识库**——操作系统、计算机组成原理、编译原理、数据结构、离散数学等**完整的计算机通识**，集中放在 `side-topics/` 里。主线文章会提供"想深入了解"的链接，但不会强制你离开主线。

::: tip 💡 什么时候去支线
主线文章里出现一个新术语时，高亮块会先给你一句够用的解释。只有当你确实想弄懂某个底层原理（比如"操作系统到底怎么管内存"）时，才顺着链接去支线细读。**支线不打断主线，主线的坑先走完再回头补。**
:::

## 人工接管：AI 卡住时，你才是负责人

课程希望培养的最终能力，是**人工接管**——AI 卡住、误解需求、反复修改，或者做出危险操作（删除数据、碰权限、动密钥、改部署）时，你能判断发生了什么，并且知道该怎么接手：

- 判断项目当前状态：文件在哪、哪个程序在跑、数据存到了哪里
- 读懂错误信息，把问题分成"我的问题 / 环境的问题 / 方案的问题"
- 设计最小的排查步骤：先确认问题 → 缩小范围 → 搜索方案
- 验证 AI 的结果：真的跑起来了吗？数据真的保存了吗？目标真的达成了吗？
- 用 Git 保存、回退、恢复，让每一步都可撤销

::: tip 💡 高光时刻
你不需要变成比 AI 强的程序员。你只需要在它开得快的时候看得懂，在它跑偏的时候拉得住。**对最终结果负责的，是你。**
:::

## 读完这一章，接下来去哪

这一章没有教你任何命令，因为你还没到需要它们的时刻。下一站是主线真正的第一步——**创建项目**：AI 会突然变出一堆文件，你要弄明白它们是什么、从哪来、有什么用。这会引出一门课最基础的两个概念：**文件系统**和**项目结构**。

::: tip 💡 本节收获
- 和 AI 一起做项目，会经历"提出需求 → 部署分享"的完整旅程
- 课程采用双线结构：主线做项目，理论线按需解释，Build Lab 手动巩固，支线放深挖
- 你的最终角色不是写代码，而是**理解、判断、控制与接管**

:::

## 📖 本章术语

| 术语 | 一句话解释 |
|------|-----------|
| **主线** | 贯穿课程的实践线：把一个真实项目从零做到上线 |
| **理论线** | 由主线问题引出的知识线，按需出现，不打断主线 |
| **Build Lab** | 关掉 AI 手动完成的集中实验，用来形成系统地图 |
| **支线知识库** | 完整的计算机通识文章，供主线之外深入阅读 |
| **人工接管** | AI 失效或危险时，由人判断状态、设计排查、验证结果并控制风险 |
| **依赖 (Dependency)** | 项目引用、借用的第三方现成代码，需要安装后才能运行 |
| **部署 (Deploy)** | 把本地项目发布到服务器上，让它对别人可访问 |
